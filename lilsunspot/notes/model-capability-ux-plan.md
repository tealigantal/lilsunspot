# 模型能力与用户引导总计划

日期：2026-06-13

目标：把“小黑子能不能完成用户当前这件事”变成产品级能力编排，而不是靠单点补丁、关键词判断或让用户自己理解模型差异。用户只需要表达自然需求；小黑子负责判断需要哪些能力、当前配置缺什么、应该引导用户接入什么，并在失败时给出可理解的下一步。

本文是后续模型、图片、文件、微信、模式和工具链路改造的主计划。具体实现仍按 `TASKS.md` 分阶段进入 `Current`，但不得再绕过本文的链路设计直接做窄修补。

## 核心原则

1. 不让用户理解 provider 细节。用户不需要知道 DeepSeek、Qwen、OpenRouter、OpenAI-compatible、本地 Ollama 的能力边界；产品要在合适的时间告诉用户“现在能做什么 / 还缺什么 / 一键怎么补”。
2. 不用关键词触发关键行为。Mode 切换、图片识别、文件处理、微信发送、工具调用等不能靠固定关键词判断；必须走结构化意图、能力预检、状态机和必要确认。
3. 先做能力图，再做 UI。所有入口都读取同一份 capability graph，避免设置页显示“可用”，聊天页又说“不支持”。
4. 能自动判断的不要问用户。只有涉及费用、账号、外部发送、高风险动作、安装依赖或隐私边界时才要求用户确认。
5. 失败必须可解释。错误展示要说明阶段、原因和可执行建议；不能只说“请求失败，请稍后再试”。
6. 所有链路都要覆盖误触。空 Key、错模型、错 Base URL、重复点击、半保存、断网、额度不足、切到文本模型后上传图片、发送后附件仍残留，都要有可预期结果。
7. 不记录 secret。Key、token、微信凭据、私聊正文、附件原文、截图中的私密内容不得进入日志、诊断、prompt、fixture 或文档。

## 用户行为假设

普通用户可能会这样使用小黑子：

- 直接选择熟悉或便宜的主模型，例如 DeepSeek、qwen-plus，而不知道它不能看图。
- 先保存主模型，之后才拖入图片、PDF、截图、表格或微信文件。
- 看到“图片识别模型已保存”后，期待下一张图一定能被识别。
- 不知道 API Key 从哪里拿，也不知道 Base URL 是否要改。
- 把视觉模型 Key 粘到主模型 Key，或把主模型 Key 粘到视觉模型 Key。
- 重复点击保存、继续、测试连接，或在保存中切换 provider。
- 在微信里自然说“换成温柔一点”“这张图帮我看看”“把这个文件发给他”，不会用 slash command。
- 不知道当前是哪个对话、微信消息会进入哪里、模型是否还在生成。
- 遇到失败时只关心“我该点哪里修好”，不关心内部错误码。

因此，产品计划必须围绕“猜测用户真正想完成的事”，而不是只围绕用户点击了哪个控件。

## 能力图

后续应建立统一 capability graph，来源包括：

- provider registry：provider、推荐模型、官方入口、Key 获取入口、Base URL 默认值、是否本地服务、是否支持 OpenAI-compatible。
- Hermes model metadata / image routing：主模型是否原生支持图片、辅助视觉是否配置、输入模式是 native image 还是 text summary。
- 本地配置状态：主模型、fallbacks、auxiliary.vision、API Key 是否存在但不回显、Base URL 是否覆盖。
- 运行时探测：测试连接、模型名是否存在、额度/限流/鉴权失败、网络失败。
- 产品能力开关：微信、文件、提醒、记忆、搜索、工具、安全审批。
- 当前入口状态：桌面聊天、微信入站、设置页、首启向导、安装版 daemon、离线/本地模型。

统一输出至少包括：

- `capability_id`：如 `chat.text`、`image.read`、`file.pdf.read`、`weixin.send_file`、`mode.adjust`。
- `status`：`ready | needs_setup | degraded | blocked | unknown`。
- `source`：主模型、辅助模型、本地 parser、Hermes toolset、微信 runtime 等。
- `blocking_reason`：脱敏的机器可读原因。
- `user_message_cn`：普通用户可读说明。
- `next_actions`：打开官网、保存 Key、选择推荐模型、继续文字聊天、稍后再试、切换服务。
- `last_verified_at`：最近一次测试或推断时间，区分“已配置”和“真实可用”。

## 意图与能力预检

所有用户入口在执行前先做预检：

1. 收集输入：文字、图片、文件、微信 route、当前对话、当前 mode、用户是否正在设置。
2. 判断意图：聊天、识图、读文件、发微信、改模式、创建提醒、搜索资料、生成文件、修复设置。
3. 推导能力需求：例如“带图片聊天”需要 `image.read + chat.text`；“把文件发给微信”需要 `file.exists + weixin.connected + safety.approval`。
4. 查询 capability graph。
5. 若能力 ready，执行链路。
6. 若能力 needs_setup，给出最短配置路径。
7. 若能力 degraded，继续执行可用部分并明确限制。
8. 若能力 blocked，说明原因和修复动作。

Mode 变化不得再靠关键词。推荐路线：

- 使用结构化 intent router，输出 `intent=mode.adjust | chat.normal | tool.request | unclear`、置信度、目标 mode、需要确认的点。
- 低置信度时先正常聊天或追问，不静默改模式。
- UI 按钮、微信自然语言和设置页都写入同一 mode state。
- mode state 变化要有事件、会话记录和可撤销入口。

## 模型编排策略

小黑子至少要区分这些模型角色：

- 主聊天模型：负责日常对话、总结和推理。
- 辅助视觉模型：负责图片识别，输出中文摘要给主聊天模型。
- 文件解析器：PDF、docx、xlsx、csv、txt、md，本地优先。
- 语音转写模型：后续处理音频或微信语音。
- 图像生成模型：后续生成图片时使用，不和识图混淆。
- 搜索/浏览工具：后续需要实时信息时使用。
- 本地模型：Ollama/LLaVA 等，需明确启动状态和本地依赖。
- fallback 模型：主模型失败时的备用，但不能绕过用户费用和隐私边界。

图片链路的目标状态：

```text
用户上传图片
-> 保存安全附件和预览
-> capability graph 判断 image.read
-> 主模型原生视觉可用：直接进入主模型 native image
-> 主模型不能看图但 auxiliary.vision 可用：调用辅助视觉模型生成摘要
-> 把摘要、附件名、来源和用户问题交给主聊天模型
-> UI 显示 recognized、摘要来源和可解释状态
-> 发送请求被接受后立即清空输入区附件队列；历史消息保留附件卡，但输入区不得残留已发送图片
-> 失败时保留 preview_only，并说明失败阶段和下一步
```

这要求设置页、`/providers/capabilities`、附件摘要、聊天 prompt 和消息气泡都使用同一个能力结果。不能出现“设置页已可用，聊天页仍只看主模型”的分裂。

## 用户引导

首启和设置页：

- 用户选择主模型后，立即展示能力摘要：文字、图片、文件、微信、工具。
- 如果主模型不能看图，主动解释：“这个模型适合文字聊天，但不能直接看图片。”
- 给出两个清晰路径：“继续文字聊天”和“添加图片识别模型”。
- 添加图片识别模型时显示官方入口：Key 页面、模型文档、Base URL 说明。
- 已保存 Key 时只显示“已保存，可留空更新其他项”，不回显 Key。
- 保存后不要只说“保存成功”，还要显示“是否已真实验证”。

聊天时：

- 用户第一次上传图片且没有识图能力时，在附件卡和回复区都给出引导。
- 用户已经配置辅助视觉但调用失败时，显示“图片已保存和预览，识别失败在：辅助视觉模型鉴权/额度/模型名/Base URL/网络”。
- 用户使用文本主模型加视觉辅助时，回复中不要说“当前模型不能识别图片”，而应说明“图片已由图片识别模型读取，当前聊天模型基于识别结果回答”。
- 发送图片后，输入区附件列表应清空；若发送失败才恢复待发送附件，避免用户误以为图片还没发送或下一条消息重复带图。

微信时：

- 微信图片入站应走同一图片链路。
- 不能识图时回复微信端普通中文说明，并在桌面设置里提示一键补齐。
- 微信端自然语言切换 mode、切换对话、发文件都要走结构化意图和确认，不走固定关键词。

## 错误分类

后续错误至少按阶段记录和展示：

- `setup.missing_key`：缺 Key。
- `setup.invalid_key`：Key 被拒绝。
- `setup.model_not_found`：模型名不可用。
- `setup.base_url_invalid`：Base URL 格式或服务不可达。
- `provider.quota_exceeded`：余额或额度不足。
- `provider.rate_limited`：请求过快。
- `provider.network_error`：网络、本地服务或代理问题。
- `capability.unsupported`：当前模型或工具不支持该能力。
- `vision.auxiliary_failed`：辅助视觉调用失败。
- `vision.native_failed`：主模型原生视觉调用失败。
- `file.parse_failed`：文件解析失败。
- `weixin.disconnected`：微信未连接或断线。
- `safety.approval_required`：需要确认后才能执行。
- `agent.loop_failed`：Hermes agent loop 异常。

用户可见文案必须包含：

- 发生阶段。
- 普通中文原因。
- 下一步按钮或建议。
- 不包含 Key、token、完整私密路径、原始 traceback。

## 验收矩阵

每个模型/能力相关改动都要覆盖这些维度：

- 主模型：DeepSeek 文本模型、Qwen 文本模型、Qwen-VL、OpenAI/OpenAI-compatible、OpenRouter、本地 Ollama、本地 LLaVA。
- 输入：纯文字、图片、PDF、docx、xlsx/csv、多个附件、微信图片、微信文件。
- 配置：未配置、Key 缺失、Key 错误、额度不足、模型名错误、Base URL 错误、已保存 Key 留空更新、清除辅助模型。
- 用户误触：重复点击保存、保存中切换 provider、空表单保存、继续文字聊天后再上传图片、发送图片后附件输入区不残留、发送失败时附件可恢复、删除对话后入站、断网后重试。
- 入口：首启向导、设置抽屉、桌面聊天、微信入站、安装版启动恢复。
- 视口：960x680、390x760，错误提示和主要按钮首屏可见，无横向溢出。
- 安全：日志、诊断包、prompt、fixture、截图不含 secret。

## 阶段路线

### Phase 1：统一能力图和状态口径

- 建立统一 capability graph。
- `/providers/capabilities` 不只返回“配置存在”，还区分“已配置/已验证/推断可用/真实失败”。
- 设置页、首启、聊天附件卡、控制台统一读取同一结果。
- 补回归测试：辅助视觉存在但未验证时不误导为真实可用。

### Phase 2：辅助视觉真实接入图片链路

- `describe_image_data_url()` 支持主模型 native image 和 `auxiliary.vision` 两条路径。
- 辅助视觉输出摘要后交给主聊天模型。
- 附件状态从 `preview_only` 正确转为 `recognized`。
- 错误 metadata 记录脱敏阶段和原因。

### Phase 3：普通用户配置引导

- 给所有视觉 provider 加官方入口和说明。
- UI 提供“获取 Key”“查看模型说明”“什么时候改 Base URL”。
- DeepSeek/qwen-plus 等文本模型保存后主动提示图片能力缺口。
- 用户不用自己判断是否要接入视觉模型。

### Phase 4：结构化意图路由

- 替换 mode/工具/微信命令中的关键词判断。
- 引入结构化 intent result、置信度、确认策略和事件记录。
- 用户自然语言表达 mode 变化、对话切换、文件发送时走状态机。

### Phase 5：全链路可解释错误

- 后端统一错误码和阶段。
- 前端错误气泡显示原因、建议、操作按钮。
- 控制台/诊断包只显示脱敏摘要。

### Phase 6：安装版和真实账号验收

- 安装版 NSIS smoke。
- 真实安全测试凭据覆盖主模型、辅助视觉、微信图片/文件。
- 视觉验收截图覆盖桌面和移动视口。

## 当前优先级

第一刀不是单纯加链接，而是修通“保存视觉模型 -> 上传图片 -> 辅助视觉识别 -> 主模型回答 -> 用户看到可信状态”的闭环。

完成标准：

- DeepSeek 或 qwen-plus 作为主模型时，用户上传图片不会被要求理解模型差异。
- 如果没有视觉能力，小黑子主动引导添加。
- 如果配置了辅助视觉，小黑子真实使用它。
- 如果失败，小黑子说清楚失败在哪一步。
- 同一状态在设置页、聊天页、附件卡、控制台一致。

## 2026-06-14 全页面状态 contract 落地记录

- 本轮把首启、模型设置、图片识别、聊天输入区、设置抽屉、能力页、控制台、安全页和输出模式页收口到共享前端状态语义：主动作结果、能力刷新、局部页面读取和聊天 turn 状态分层处理。
- `AppShell` 持有 provider 列表和 `ModelCapabilities`；首启、设置页、图片识别面板、聊天输入区和能力/控制台读取同一份能力状态，避免重复提示和旧状态。
- 保存主模型、重配模型、保存/清除辅助视觉后，能力刷新失败只显示“稍后刷新”的非阻塞提示，不再把已成功保存渲染成“当前步骤没有完成”。
- 能力页、控制台、安全页、输出模式页改为分区读取；一个接口失败不会清空其它区已有数据。
- 聊天页不再创建本地 assistant 假失败泡泡；本地只显示可自动清除的发送确认提示，后端 message/event 到达后按 server message 合并。
- 聊天气泡不再显示内部 `engine` / Hermes 名称；附件交付只显示中文状态和安全附件卡。
- Provider Key 跳转增加多 provider 回归，确保只使用当前产品 provider 的 `key_url`，不退回 `detect_url` 或 Base URL。
